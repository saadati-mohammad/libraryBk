## Permission contract (verified baseline)

- Guest: read public catalog and details only; reset/login/register public operations; phone scan submission requires possession of a short-lived capability token.
- MEMBER: public catalog plus own `/api/account/**`; server determines identity from authentication, never a user-supplied member ID.
- LIBRARIAN: shared book/person/loan/reservation/dashboard/import operations under backend staff role matcher; no staff-account administration.
- ADMIN: librarian operations plus staff account operations under `/api/admin/**`.
- All remaining API endpoints require authentication; UI route guards are not an authorization boundary. Message/file access also has participant checks; orphan attachments fail closed (T-022 DONE).

## Current test map and gaps

- UI (latest): 30 Vitest files / 162 tests; Playwright Chromium desktop/mobile 75 pass and one viewport-conditional skip (76 total); headed input-device flow passed. Coverage includes device management, catalog, login/member/staff, books/people, loans/reservations, date/calendar, password reset, barcode modes, accessibility and contrast. Import dry run, session administration, permission matrix, complete audit center and physical-copy inventory remain open.
- API (latest): Maven `clean verify` 161 tests on H2/Flyway. Tests cover auth/reset/throttling, device registry/auth/rate limiting, role enforcement, member ownership, soft delete, file path/participant authorization, imports, scanner relay, reservation, and aggregate concurrency. MySQL execution, identity-session revoke, fine-grained policy engine, physical copy, unified audit center, and load/backup drill remain open.
- Treat every `Gap` as an explicit implementation task. Scenarios dependent on email/SMS, real scanner hardware, RFID, multiple branches, third-party Iranian catalog licensing or production MySQL must have a runnable adapter test and deployment evidence before being marked complete.
